# Local-Deep-Research-Perplexity-Magazine-style

**一套在本地复刻并升级 Perplexity Deep Research 体验的「多元深度调研 + 大众人文杂志风格长文写作」完整系统。**

---

## 一、 这个 Skill 是什么？它能做什么？

当你向普通的 AI 提出一个复杂的研究课题（例如：*“调研某项前沿技术的演进脉络与行业争议”* 或 *“剖析某类创作者背后的思维训练机制”*）时，常规 AI 的回答往往存在三个致命缺陷：

1. **只看搜索摘要（Snippets），不读原文**：AI 扫一眼搜索引擎返回的前几行摘要就开始拼凑答案，缺乏一手原文中的真实细节、核心数据、人物原话与反方视角。
2. **浓重的“AI 八股目录味”**：AI 极度依赖“一、背景；二、现状；三、核心特点；四、未来展望”的僵硬大纲，并在每个小标题下堆满碎片化的列表（Bullet Points），读起来像一份干瘪的公文提纲，毫无阅读快感。
3. **搜索过程噪音污染了写作注意力（最核心的隐形杀手）**：在一轮或多轮联网调研中，AI 的主会话上下文（Context Window）里会堆积数万字的网页残渣、死链报错、导航栏乱码与工具调用 JSON。如果让同一个会话顺着这堆“上下文垃圾”直接往下写报告，哪怕是最顶级的模型，其文笔质感、叙事连贯性与思想深度也会断崖式下跌。

**`local-deep-research` 正是为了彻底解决这三个问题而设计的。**

它的核心能力是：**将「多源深度调研」与「杂志级长文撰写」拆解为两个物理隔离的阶段**——先调动多元搜索工具与全文抓取链完成扎实的一手证据搜集，由调研模型剔除所有过程杂音、提纯出一份包含「无序论点地图」的**干净写作资料包（`writer-packet.md`）**；随后启动一个**全新的、极短且零干扰的独立上下文**，交由公认文笔最优异的撰写模型（如 Claude Opus 5.5/4.5、Claude Sonnet 5.5、Gemini 4 Argon / Pro、Gemini 3.7/3.8 Flash 等），写出一篇像《纽约客》《三联生活周刊》《经济学人》深度特稿那样自然流动、娓娓道来的杂志长文。

## 二、 关于本仓库采用「Agent 引导自部署」的特别说明

船板此前曾制作过第一代固定脚本版的深度研究与杂志写作 Skill（现仅归档于旧分支作个人历史留存，**请完全忽略旧版本，切勿阅读或参考旧分支的任何内容**）。

当前船板对最新版本进行了从底层架构到工作流的彻底重构。由于新版的完整运行涉及多源搜索组合、两阶段上下文物理隔离以及本地多模型路由（最佳体验依托于 **MaGpie** 等本地模型路由网关），而不同用户的电脑操作系统、宿主 Agent（Claude Code / Codex / Cursor / Windsurf / OpenCode 等）、已配置的搜索工具及模型接入方式千差万别，直接分发一套写死路径与接口的硬编码脚本极易在他人电脑上水土不服。

**因此，本仓库采用全新的「Agent 引导自部署（Agent-Guided Self-Deployment）」方式发布：**
- **本指南与配套文档是一份从零开始、完全独立自足（Standalone）的完整系统蓝图。**
- 文档中的所有端口、模型 ID、网关前缀与脚本实现均为**可替换的启发式占位与参考示例**，而非死板的硬性绑定。
- 你不需要去看任何历史版本，也不需要自己手动折腾环境配置。**只需要让你的 AI Agent 完整阅读本 `README.md`、`SKILL.md` 及 `references/` 目录中的文档，你的 Agent 就能从头到尾彻底理解整套系统的每一个设计环节、路由机制与避坑要点，并主动引导你（用户主人）根据你电脑的实际情况现场裁剪、完成本地化部署与使用。**

### 关键节点详解 1：双工作模式设计（兼顾日常高频办公与学术级重度深研）

本系统在同一个 Skill 内提供两种工作模式，**默认直接进入模式一**：

| 维度 | 模式一：快速杂志报告模式（`Fast Mode`，默认） | 模式二：标准重度 Deep Research（`Full Mode`） |
|------|--------------------------------------------|----------------------------------------------|
| **设计初衷** | 模仿 Perplexity 网页端体验：给出一个题目后，快速用近似深研的多源检索与原文精读，输出兼具深度和可读性的杂志文章 | 标准意义上的本地学术级重度 Deep Research：多轮动态补搜、滚动洞察传递、严格门禁、逐句蕴含审计 |
| **搜索与阅读深度** | 1 轮多元组合搜索 + 精读约 3–5 篇核心原文（按需追加 1 次补漏） | 初始双查询包 + 动态多轮补搜（建议 2–6 轮，视课题复杂度而定）；每轮精读约 3–6 篇 A/B 级权威原文 |
| **过程门禁** | **豁免脚本门禁**，不建繁琐中间文件 | **启用滚动研究记忆（Insight Gate）门禁**：每轮提炼带唯一 ID 的核心洞察，向下一轮传递上下文快照与回执 |
| **撰写阶段逻辑** | **与模式二 100% 完全相同**：主会话提纯生成 `writer-packet.md` → 独立干净上下文撰写模型产出 `report.md` | **与模式一 100% 完全相同**：从通过门禁的 `outline.md` 与 `evidence-ledger.md` 提纯生成 `writer-packet.md` → 独立干净上下文撰写模型产出 `report.md` |
| **写后核验** | 轻量内联核验（核对关键事实与数字无误即可） | 独立逐句扫描报告内全部可证伪主张，输出 `citation-audit.md`（区分 `direct / synthesis / editorial` 与 `supported / partially_supported / unsupported`），对缺口做补搜或降级改写 |
| **磁盘文件数量** | **仅 2 个文件**：`writer-packet.md` + `report.md` | **完整过程工件 + `writer-packet.md` + `report.md`** |

### 关键节点详解 2：为什么「调研」和「撰写」必须分开？怎么分？

很多人在复刻 Deep Research 时只关注“怎么搜得更多”，却忽略了**“谁来写、在什么样的上下文里写”**。
- **反面做法**：让主会话 Agent 在搜了 20 次网页、上下文累积了数万 tokens 杂乱信息后，直接说“现在请把以上内容写成一篇报告”。此时模型的注意力被大量低质量网页文本稀释，写出来的文章不仅容易遗漏重点，而且语言极其机械。
- **本系统的标准做法（两阶段物理隔离）**：
  1. **调研阶段（Stage 1）**：主会话 Agent 扮演“调查记者与编辑”，把网撒开，把原文读透，然后坐下来做减法——把所有噪音全部扔掉，只把最核心的事实、最传神的原话摘录和无序论点浓缩成一份高密度的 **`writer-packet.md`（干净写作资料包）**。
  2. **撰写阶段（Stage 2）**：通过外部路由脚本或原生空白子代理（Subagent），开启一个**全新的、只有几千 tokens 的纯净上下文窗口**。在这个窗口里，撰写模型看不到任何搜索过程，它面前只有一份干净精炼的 `writer-packet.md` 和一段要求极高的杂志主笔提示词。

### 关键节点详解 3：调研模型与撰写模型如何分配？

- **调研模型（Research Model）—— 任意可用主力模型均可**：
  - 调研阶段重在任务拆解、工具调用（Bash / Search / Fetch）和信息去噪提纯。主会话当前正在运行的任何主力模型（无论是 Claude、GPT、Gemini、DeepSeek 还是 GLM）都能胜任。
- **撰写模型（Writer Model）—— 优先选用公认文笔与叙事质感最好的模型**：
  - 撰写阶段直接决定最终成稿的中文语感、叙事节奏与人文厚度。在正常标准状态下，Agent 应根据当前用户环境实际可用的模型池，在开场提供公认写作能力最强的几个模型档位供用户选择（以下为推荐的语义档位，Agent 在部署时可根据用户实际拥有的渠道自动映射或增删）：
    1. **Claude Opus 系列**（如 `Claude Opus 5.5` / `Claude Opus 4.5` 等，旗舰级深度叙事与人文厚度）
    2. **Claude Sonnet 系列**（如 `Claude Sonnet 5.5` 等，均衡流畅，逻辑与文采兼备）
    3. **Gemini Pro / Argon 系列**（如 `Gemini 4 Argon` / `Gemini Pro` 路由组或旗舰版，极强的跨学科综合与宏大叙事结构感）
    4. **Gemini Flash 系列**（如 `Gemini 3.7 Flash` / `Gemini 3.8 Flash` 等，响应极快、性价比极高的日常轻快杂志文主笔）
    5. **跟随当前主进程模型**（当处于免问快速状态、问答超时跳过，或用户要求“不要问，直接写”时的默认兜底选项，同样在独立干净上下文中调用）。

### 关键节点详解 4：路由具体怎么用？（以 MaGpie 为典型示例，自适应各种环境）

#### 1. 什么是 MaGpie 路由？在本系统中如何工作？
在配置了本地 **MaGpie** 多模型路由网关（或其他类似本地代理网关如 LiteLLM / NewAPI / OneAPI）的环境中：
- **MaGpie 的工作原理**：MaGpie 在本机后台监听本地端口（常见默认地址如 `http://127.0.0.1:3425`，具体端口以用户本机环境变量 `ANTHROPIC_BASE_URL` / `OPENAI_BASE_URL` 或实际配置为准），将用户配置的多个上游模型供应商（格式通常为 `<provider>/<model-name>`）以及智能负载均衡路由组（格式通常为 `group/<group-name>`，如 `group/argon`、`group/gemini` 等）统一聚合在同一个本地入口下，对外提供标准的 Anthropic `/v1/messages`、OpenAI `/v1/chat/completions` 与 `/v1/models` 接口。
- **动态语义匹配路由（而非写死模型 ID）**：
  1. **实时模型池探测**：路由器或 Agent 请求本地网关的 `/v1/models` 接口，动态获取当前用户电脑上实际在线的所有模型 ID、展示名（`display_name`）与标签（`magpie_label`）。
  2. **按语义模糊匹配**：因为每个用户接入的上游供应商前缀各不相同，切勿在代码里硬编码某一家特定供应商的前缀。应根据用户选择的档位（如 `Claude Opus 5.5`、`Claude Sonnet 5.5`、`Gemini 4 Argon`、`Gemini 3.7/3.8 Flash`），在 `/v1/models` 返回的在线列表中按语义关键词动态匹配（若存在对应的 `group/*` 路由组则优先使用路由组）。
  3. **发起独立流式撰写请求**：读取 `<run-dir>/writer-packet.md`，拼装好「标准杂志主笔 System Prompt」，向本地网关发起 **`stream: true`（SSE 流式）** 请求，将返回的正文写入 `<run-dir>/report.md`。

#### 2. 如果对方用户的电脑「没有安装 MaGpie」怎么办？
对方 Agent 在帮用户部署时，会先自动探测环境。若未检测到本地 MaGpie 网关，Agent 会根据用户电脑的实际情况引导选择以下任意一种完全等效的方案：
- **替代方案 A（零配置首选：使用宿主原生的空白 Subagent 工具）**：
  - 如果用户使用的是 Claude Code、Cursor 等支持原生子代理（`Agent` / `Task` 工具）的宿主，**甚至不需要编写任何外部 Python 路由脚本，也不需要配置任何额外 API Key**！
  - 主会话写好 `writer-packet.md` 后，直接调用宿主的 **`Agent`（子代理）工具**（若支持 `model` 参数还可直接传入用户选定的模型档位）派生一个全新的空白上下文子代理，让该子代理只读取 `writer-packet.md` 并写出 `report.md`。
- **替代方案 B（用户有 OpenRouter / DeepSeek / 硅基流动 / 自建网关等单 Key API）**：
  - 将路由脚本或调用地址指向用户提供的 API Endpoint，从本地 `.env.local` 读取用户的 API Key，以标准 `/chat/completions` 或 `/v1/messages` 发送 `writer-packet.md`。
- **替代方案 C（纯 CLI 终端无状态调用）**：
  - 通过宿主 CLI 的无状态非交互命令（如 `claude --print --no-session-persistence --tools=""` 或 `codex exec --ephemeral --sandbox read-only`）将 `writer-packet.md` 从标准输入喂入独立子进程。

### 关键节点详解 5：双重主动引导机制（安装引导 + 每次调研开场引导）

一个优秀的深研写作系统，绝不能闷头瞎猜用户的意图。本 Skill 强制要求 Agent 在两个环节做好充分的主动引导：

1. **环节一：首次安装时的环境探测与部署引导**
   - 对方 Agent 读取本仓库后，先帮用户自动检查电脑上有什么（有无 MaGpie 或本地网关、有哪些搜索工具或已存的 API Key、宿主支持哪种独立上下文方式），向用户清晰展示检测结果，询问用户希望采用哪种配置方案，然后根据用户环境现场生成或裁剪适配文件。
2. **环节二：每次撰写调研稿开场时的 `AskUserQuestion` 交互引导**
   - 当用户提出一个调研题目时（除非用户明确说“不要问，直接写”或已在指令中给出了完整参数），Agent 在开始大规模搜索前，**必须主动向用户发起一次开场确认（优先使用宿主的 `AskUserQuestion` 工具）**：
     - **问题 1（厘清课题方向与重点）**：针对用户的题目，快速列出 2–3 个最核心的切入视角或潜在边界，请用户确认或指明侧重点；
     - **问题 2（确认工作模式）**：使用默认的「模式一：快速杂志报告（Fast Mode，快速出稿）」还是「模式二：标准重度深研（Full Mode，完整工件 + 多轮洞察门禁 + 逐句审计）」；
     - **问题 3（指定撰写阶段的主笔模型）**：让用户从当前环境实际可用的优质写作模型档位（如 `Claude Opus 5.5/4.5`、`Claude Sonnet 5.5`、`Gemini 4 Argon`、`Gemini 3.7/3.8 Flash` 或 `跟随当前主进程模型`）中选定主笔。

## 四、 实战踩坑总结（对方 Agent 部署与编码时务必注意的经验）

1. **【经验 1：注意思考链（Reasoning）模型的输出 Token 预算】**
   - `Claude Opus 5.5`、`Gemini 4 Argon`、`Gemini 3.7/3.8 Flash`、`DeepSeek R1` 等模型内置了深度思考（Thinking/Reasoning）。在许多网关中，`max_tokens` 是思考 token 与正文输出 token 的总和。如果把 `max_tokens` 设得过小（如 `4096`），模型光思考就会耗尽额度，导致正文写到一半被截断。
   - **启发式建议**：调用 HTTP 撰写接口时，建议将 `max_tokens` 设为较大的安全值（如 **`32768`**；若个别网关或模型报参数上限错误，脚本应自动捕获并回退到 `16384` 或网关支持的最大值）。
2. **【经验 2：长文生成建议使用流式传输（Streaming）防超时】**
   - 撰写一篇 6,000–10,000 字的杂志风长文通常耗时 60–130 秒。如果使用非流式（`stream: false`）同步阻塞等待，不少本地网关或反向代理会在 60 秒无数据返回时断开连接。
   - **启发式建议**：通过 HTTP 接口调用撰写模型时，优先开启 `stream: true`（SSE 流式接收），边接收增量文本块边拼接。
3. **【经验 3：切勿把 `writer-packet.md` 写成带序号的目录】**
   - 只要在传给撰写模型的资料包里出现“第一部分、第二部分、第三部分”或预先拟好的小标题，撰写模型就会放弃叙事思考，退化成按点填空的机器。
   - **核心契约**：资料包中的论点地图必须保持 `[U-01]`, `[U-02]` 这样的中性无序集合形态，并在提示词中明确禁止按原顺序充当目录或照抄单元标签。
4. **【经验 4：多元互补搜索与免 Key 原文读取保底】**
   - 只看搜索引擎返回的百字摘要（Snippet）动笔，会导致文章悬浮空洞。
   - **启发式建议**：根据用户环境组合使用可用搜索源；搜出候选后，**每轮务必挑选数篇核心来源读取全文正文**。若用户电脑未配置专用网页抓取工具，可直接使用免 Key 的 `https://r.jina.ai/<目标URL>`（配合 `Accept: text/markdown` 请求头）拉取干净的 Markdown 正文。
5. **【经验 5：切勿在大目录跑全盘递归 `.env` 扫描】**
   - Agent 在帮用户检查本机是否已有搜索 API Key 时，切勿对用户主目录 `~` 跑无限制的递归 `find / glob("**/.env*")`，遍历 `node_modules` 或云盘目录极易导致终端超时。应仅检查当前环境变量或已知的常规配置路径。
